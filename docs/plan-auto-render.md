# 計画: 描き方の「自動」の判定を良くする

式の ⚙ の描き方（自動 / メッシュ / 画素ごと（GPU））の「自動」を、端末の種類ではなく、その端末でその式を描く速さで決めるようにする。
決めてもらうことは 3 章。**2026-11-25 に 3 つとも案 A（おすすめ）に決まった**（`plan-performance.md` の D1〜D3）。実装の指示書は `plan-performance.md` の O1・O2。

## 1. 今の決まり

`web/src/lib/renderMode.ts` と `Viewer.ts` の 2 段。

1. **端末で決める**（`gpuByDefault`）: `matchMedia('(pointer: coarse)')`（主な入力が指）なら、自動はいつもメッシュ。それ以外は画素ごと（GPU）。
   計画 12 章の G0 で「スマートフォンは実機で測ってから決める」とした仮の決まりのまま
2. **式で決める**（`checkAborts`。3D の光線だけ）: GPU で描けるようになった後、横 192 画素の小さな描画先に一度描き、
   打ち切った画素が 15 % を超えたらメッシュに回して ⚙ に理由を出す（`mod(x y, z) = 0` など）

URL の `?gpu2d=0`・`?gpu3d=0` と、⚙ で「メッシュ」「画素ごと」を選んだときは、自動の判定を使わない。

## 2. 困ること

| # | 困ること | 例 |
|---|---|---|
| 1 | 指で操作する端末は、GPU が速くてもいつもメッシュ | 最近のスマートフォン・iPad では、ジャイロイドや `x y z = 1` の極の近く（メッシュとの差 1〜2 %。12.7 の表）が、画素ごとのほうがきれいなのに使われない |
| 2 | マウスの端末は、GPU が遅くてもいつも画素ごと | GPU の無い仮想マシン・リモートデスクトップ（ソフトウェアの描画。SwiftShader・llvmpipe・Microsoft Basic Render Driver）、古い内蔵 GPU。重い式で 1 コマ数百 ms になり、止まっているときの絵も出るのが遅い |
| 3 | 速さを見ていない | 打ち切りの割合は見るが、1 コマの時間は見ない。同じ端末でも、球は速くジャイロイドを拡大すると遅い、の違いを区別できない |
| 4 | 判定が式の表示の後 | `checkAborts` は光線の箱を画面に出した次のコマで動く。遅い端末では、メッシュに回す前に重い 1 コマを描いてしまう |
| 5 | 2D の画素ごと（gpu2d）は式の判定が無い | 端末の決まりだけ |

「スマートフォンかどうか」は速さの代わりの目安に過ぎず、外れる向きが両方ある（1 と 2）。実機で測ってから決める、という G0 の宿題は、
端末ごとに測る仕組みを入れれば、こちらで機種を調べなくても端末が自分で決められる。

## 3. 直し方の案と、決めてもらうこと

### 3.1 端末の決まりを、測った速さに替える

- **案 A（おすすめ）**: `pointer: coarse` の決まりをやめる。自動のときは、どの端末でも次の順に決める
  1. WebGL2 が無い、または描画がソフトウェア（`WEBGL_debug_renderer_info` の名前が SwiftShader・llvmpipe・Basic Render など）→ メッシュ
  2. 式ごとに、GPU のシェーダーができたら、画面に出す**前に**小さな描画先で時間を測る（3.2）。見積もった 1 コマの時間が目安を超えたらメッシュ
  3. 打ち切りが 15 % を超えたらメッシュ（今のまま）
  4. どれにも当たらなければ画素ごと
- 案 B: スマートフォンは今のままメッシュで、2 と 3 だけ足す（困ること 2〜5 は直るが、1 は直らない）

**決めること 1**: 案 A か案 B か。

### 3.2 速さの測り方と目安

- 測り方: 今の打ち切りの確かめ（`abortRatio`）と同じ描画で、「止まっているとき」の設定（区間演算の上限 4096）のまま、
  横 96 画素と 192 画素で 2 回ずつ描いて `readPixels` で待ち、時間の差から **1 画素あたりの時間** $c$ を出す
  （大きさの違う 2 回の差を使うと、描画の呼び出しなどの決まった時間が消える）。打ち切りの割合も同じ描画で数えるので、増える描画は 3 回
- 見積もり: 画面の画素数を $N$（画素密度込み）として $T = c \cdot N$
- 目安: **案 A（おすすめ）** $T \le 50\,\mathrm{ms}$（G0 で決めた目安と同じ。止まっているときの 1 コマ）。動かしている間は今の `motionQuality` が画素密度・光線の回数を下げる
  - 案 B: $T \le 33\,\mathrm{ms}$（電池・発熱を気にして厳しめ）
- 判定は式の GLSL ごとに 1 回（式・パラメータの形が変わって GLSL が変われば測り直す）。画面を回転して $N$ が変わっても測り直さない（行ったり来たりしないように）
- 理由を ⚙ に出す: 「この端末では画素ごとの描き方が重いので（見積もり 1 コマ 120 ms）、メッシュで描いています（画素ごと（GPU）を選ぶと使えます）」

**決めること 2**: 目安 50 ms（案 A）か 33 ms（案 B）か。

### 3.3 測った結果を覚えるか

- **案 A（おすすめ）**: 覚えない。式ごとに毎回測る（増える時間は小さな描画 3 回。速い端末で 1 ms 前後、遅い端末でも 192 画素の描画なので画面全体の 1〜2 % の時間）
- 案 B: 端末の速さ（基準の式の $c$）を `localStorage` に覚え、とても遅い端末は測らずにメッシュにする（最初の式の表示が少し速くなるが、
  ブラウザの更新・電源の設定で速さが変わったときに古い値を使う）

**決めること 3**: 案 A か案 B か。

### 3.4 決まっていること（正しい答えが決まっている）

- 測るのは画面に出す前（困ること 4）。シェーダーのコンパイルが終わった後・最初に画面に出す前に測り、メッシュにするならそのまま出さない
- 2D（gpu2d）も同じ測り方・目安（困ること 5）。2D には打ち切りの判定は無いので、時間だけ
- ⚙ の「この端末では、自動のときはメッシュで描きます」は、測った理由の文に替える
- `?gpu2d=0`・`?gpu3d=0`・⚙ で選んだ描き方は今のまま優先

## 4. テスト

- 判定そのもの（WebGL2 の有無・描画の名前・$c$・$N$・打ち切りの割合 → 描き方と理由）を `renderMode.ts` の、three.js に依存しない関数にして、
  `renderMode.test.ts` で表のテスト（今の `motionQuality.test.ts` と同じ形）。古い決まりでは失敗することを確かめる（指の端末で速ければ画素ごと、など）
- 時間の差から $c$ を出す計算（2 回ずつの最小値・負や 0 の差の扱い）も同じファイルで
- 実機: こちらのヘッドレスの Chromium は SwiftShader なので「ソフトウェア → メッシュ」の道を確かめられる。速い GPU の道は、依頼者のデスクトップとスマートフォンで
  ⚙ の理由の文を見てもらう
