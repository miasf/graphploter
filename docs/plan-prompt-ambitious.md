## 前提

リポジトリの構成、テストのコマンド、決まりごと（日本語のコメントと README）、GitHub Pages の制約は、
`docs/plan-prompt-hard-tasks.md` の「リポジトリの前提」と同じです。

今のエンジンで分かっていること（候補を考える土台）:
- 式の種類は、陽関数・陰関数（`=` だけ。`<` などの比較演算子は無い）・媒介変数（曲線・曲面・立体・多変数）・パラメータ・リスト
- 演算子は `+ - * / ^ !` だけ。**微分・Σ・Π・積分・場合分け・ユーザー定義関数（`f(x) = …`）は無い**（`parser.rs` の `Tok`、`BinOp`）
- 計算は命令列の VM で、たくさんの点をまとめて複素数で計算する（`eval.rs`）。同じ部分式の共有と定数の畳み込みがある
- 法線は三角形から計算している（`mesh.rs` の `compute_normals`）。式の勾配は使っていない
- 頂点の座標は f32 で GPU に送る。陰関数の格子の値も f32 で保存する
- 半透明は、不透明度が 1 未満のとき `transparent` にして `depthWrite` を切るだけ（`Viewer.ts`）

## 候補

候補ごとに「何ができるようになるか → なぜ難しいか → 先に要るもの」を書いてあります。
**A と B は、ほかの候補の土台になります。** 依存関係を見て順番を決めてください。

### A. 式の自動微分（土台）

**できるようになること**: 勾配 $\nabla F$ と偏導関数 $\partial_x f$ を、数値差分ではなく正確に求める。これを使うと、次のことができる。
- 式の中で微分を書く: `d/dx`、$\dfrac{\partial}{\partial x}$、`grad`
- 法線を式から正確に求める（陰関数なら $\mathbf{n} = \nabla F / \lVert \nabla F \rVert$）。格子が粗くても陰影がなめらかになる
- 陰関数の頂点を、ニュートン法で曲面の上へ押し戻す: $\mathbf{p} \leftarrow \mathbf{p} - \dfrac{F(\mathbf{p})}{\lVert \nabla F \rVert^2} \nabla F$
- 候補 C・F・G・H の前提になる

**難しい所**
- VM の命令ごとに、双対数（値と微分の組）で計算する版を作る必要がある。複素数の値に、実の変数 x, y, z による微分を付けることになる
- 特殊関数のすべてに導関数が要る（例: $\partial_z J_\nu(z)$ は漸化式で書けるが、$\partial_\nu J_\nu$ は難しい。$\Gamma$ には $\psi$、楕円関数・超幾何関数はそれぞれ別の公式）。導関数が無い関数を、数値微分で代用するか、エラーにするかの線引きが要る
- `abs`、`floor`、`arg` の分岐の所など、微分できない点の扱い
- 共通部分式の共有と、実数だけで計算する速い道（README の最適化）を壊さないこと

### B. 式を GLSL / WGSL に変換して、画素ごとに GPU で計算する（土台・最大の目玉）

**できるようになること**
- 陰関数を**メッシュを作らずに**レイマーチングで描く。画面の画素の細かさで描けるので、`hard-tasks` の課題 2（発散）と課題 3（小さい図形）を、別の方向から根本的に解決できる可能性がある
- 複素関数の色分けを画素ごとに計算する（拡大しても縞がぼやけない）
- スカラー場 $F(x, y, z)$ を、霧のような密度としてボリュームで描く
- スライダーを動かしてもメッシュを作り直さないので、再生が 60fps になり得る

**難しい所**
- VM の命令列を、シェーダーのコードに変換する。共通部分式は一時変数にし、ループの無い 1 本の式にする
- GPU は基本的に f32 の精度しかない。$\Gamma$、ゼータ、ベッセルなどを f32 で計算すると桁落ちが大きい。シェーダーに載せる関数の範囲を決め、載らない式は今のメッシュ方式に戻す必要がある
- 陰関数のレイマーチングでは、根を見落とさない歩幅が要る。リプシッツ定数がわからない式でどう歩幅を決めるか（候補 A の勾配、`hard-tasks` の区間演算が使える）
- 今のメッシュの曲面と、深度をそろえて混ぜて描くこと。クリッピング、断面、格子線、ピッキングとの両立
- WebGL2 だけで作るか、WebGPU を使うか（使えないブラウザでの代わりの道）

### C. 稜線を保つ陰関数のメッシュ（Dual Contouring）

**できるようになること**: `max(|x|, |y|, |z|) = 1`（立方体）や `|x| + |y| + |z| = 1`（正八面体）の角と辺を鋭く描く。
Surface Nets は頂点をセルの中で平均するので、角が丸まる。

**難しい所**
- セルの辺と曲面の交点で勾配（候補 A）を取り、QEF（二次誤差の関数）を最小にする点を頂点に置く。特異値分解でのしきい値の決め方が品質を左右する
- 頂点がセルの外に出ると三角形が裏返り、自己交差する
- 今ある「近い曲面ごとに頂点を分ける」処理と、粗い版（LOD）との両立

### D. 不等式の領域・式どうしの組み合わせ

**できるようになること**: `x^2 + y^2 + z^2 < 4`、`z < sin x cos y`、`x^2+y^2 < 1 and z > 0` のような 3 次元の領域を、半透明の立体として描く。
2D 表示なら、不等式の塗りつぶしになる。

**難しい所**
- パーサーに比較演算子と `and`・`or` を足し、MathLive の入力（`latex.ts`）にも対応させる
- 領域の境界面は、陰関数の面 $F = G$ のうち、条件を満たす部分だけを残したものになる。`and` で交わる所の鋭い辺（候補 C）を描く必要がある
- 表示範囲の箱で切った面にもふたが要る（`hard-tasks` の課題 5 と同じ問題）
- 中身が見える半透明（候補 E）が無いと見づらい

### E. 正しい半透明（順序に依存しない透明）

**できるようになること**: 入れ子の曲面、4 次元の立体の射影、不等式の領域を、重なり方が正しい半透明で描く。
今の方式では、描く順番によって、奥の面が手前の面を隠したり、隠されるべき面が見えたりする。

**難しい所**
- 重み付きの順序非依存透明（Weighted Blended OIT）か、デプスピーリングを Three.js の描画の流れに組み込む。描画の目標（render target）を複数使い、格子線のシェーダーと複素数の色分けのシェーダーの両方に対応させる
- スマホの GPU でも fps を保てるか（デプスピーリングは何回も描くので重い）

### F. ベクトル場と常微分方程式の解曲線

**できるようになること**: $\dfrac{d\mathbf{x}}{dt} = \mathbf{F}(\mathbf{x}, t)$ の解曲線（ローレンツ・アトラクターなど）、流線、矢印の場を描く。
始点をドラッグすると、解曲線がその場で描き直される。4 次元以上の流れを射影するのも、今の n 次元の仕組みに乗る。

**難しい所**
- 刻み幅を自動で調整する解法（RK45、硬い方程式なら陰的な解法）を `eval_batch` の上に作る。たくさんの始点を一度に計算すれば、まとめて計算する今の作りが生きる
- カオス的な系では、少しの誤差で見た目が大きく変わる。決まった結果になること（同じ入力なら同じ絵）を保証すること
- 入力の書き方（`x' = …` か、ベクトルで書くか）と、パラメータ・リストとの組み合わせ

### G. 曲率の色分けと、曲面の上の測地線

**できるようになること**: ガウス曲率 $K$ と平均曲率 $H$ で曲面を色分けする。曲面の上の 2 点を結ぶ測地線を描く。微分幾何の教材として強い。

**難しい所**
- 陽関数なら $K = \dfrac{f_{xx} f_{yy} - f_{xy}^2}{\left(1 + f_x^2 + f_y^2\right)^2}$ なので、2 階の微分が要る（候補 A を 2 階に広げる）。陰関数と媒介変数の曲面では、それぞれ式が違う
- 測地線は、クリストッフェル記号の入った 2 階の常微分方程式になる（候補 F の解法を使う）。2 点を結ぶには、境界値問題（撃ち込み法）を解く必要がある

### H. 点を押すと値・交点・極値がわかる

**できるようになること**: 曲面を押すとその点の座標と値が出る。2 つの曲面の交線を強調して描く。
$z = f(x, y)$ の極大・極小・鞍点に、自動で印を付ける（Desmos の「注目点」の 3D 版）。

**難しい所**
- 押した所の正確な点: 三角形との交点を、式の上でニュートン法で修正する（候補 A）
- 交線: 2 つの陰関数 $F = 0$、$G = 0$ の交わりを追跡する。接する所で不安定になる
- 極値: $\nabla f = \mathbf{0}$ の解をすべて見つけるのは一般には難しい（候補 A と区間演算）。見落としを認めるか、保証付きにするか

### I. 多価関数のリーマン面

**できるようになること**: $w = \sqrt{z}$、$\log z$、$\arcsin z$、$\sqrt[3]{z^3 - 1}$ を、分岐の切れ目で途切れない、つながった曲面として描く。
例えば、高さを $\mathrm{Re}\,w$、色を $\arg w$ にする。作れれば、ほかのグラフソフトではほとんど見られない絵になる。

**難しい所**
- 関数の値を、格子の上で**解析接続**しながら追跡する（となりの点の値に一番近い枝を選ぶ）。主値をそのまま計算すると分岐の切れ目で飛ぶので、そうならないようにする
- 分岐点の周りを 1 周したら別の枝に移る。枝の数（シート数）がわからない一般の式で、メッシュのつながりをどう作るか
- 分岐点の近くでは値の変化が急なので、細かい格子が要る（`hard-tasks` の課題 2 と同じ）

### J. 深く拡大しても崩れない描画（精度）

**できるようになること**: $\sin\!\left(\frac{1}{x}\right)$ の 0 の近くや、$10^{-10}$ の幅の表示範囲を拡大しても、形がガタガタにならない。

**難しい所**
- 頂点を f32 で GPU に送るので、原点から遠い所で狭い範囲を見ると、頂点が格子状に揃ってしまう。表示範囲の中心を引いた相対座標で送り、カメラの行列も中心からの相対にする（relative-to-center）
- 陰関数の格子の値を f32 で保存しているので、Surface Nets の交点の位置に誤差が出る
- 式の計算そのものの桁落ち（f64 の限界）。部分的に倍々精度（double-double）を使うかの判断
- 目盛りの文字・格子線・クリッピングの面を、すべて同じ座標系にそろえること

### K. 特殊関数の精度を全域で検証する仕組み

**できるようになること**: 「特殊関数がすべて複素数で使える」ことを、数字で保証する。
例えば、どの関数も、複素平面の決めた範囲で相対誤差 $10^{-12}$ 以下だと言えるようにする。

**難しい所**
- 参照値を高精度の計算（mpmath など）で作り、リポジトリにテストの表として入れる。表の大きさとテストの時間のかね合いを考える
- 苦手な範囲が見つかったら、計算方法を切り替える。例えば `bessel.rs` には「級数の桁落ちが大きく、漸近展開もまだ使えない中くらいの $|z|$」用の処理がある。そうした境目で、精度と値の連続性（境目で値が飛ばないこと）を両立させる
- 地味だが、B（GPU）や A（微分）を入れたときに、精度を確かめる土台になる
