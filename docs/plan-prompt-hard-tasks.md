## あなたの役割

あなたは graphploter（ブラウザで動く 3D グラフソフト）の技術リードです。
下の「課題」について、次のことをしてください。

1. 現状のコードを読み、問題が**本当にどこで起きているか**を確かめる（このファイルの推測が間違っていれば直す）
2. 解決の方針を複数考え、**1つを選んで理由を書く**（全部を並べるだけにしない）
3. 実装担当（Opus）向けの指示書を、**1 PR で終わる大きさのステップ**に分けて書く

## リポジトリの前提

- `core/`: Rust の計算エンジン → WebAssembly。式の解析（`parser.rs`）、命令列で一度にたくさんの点を計算（`eval.rs` の `eval_batch`、すべて複素数）、メッシュ生成（`mesh.rs`）、JS への入口（`lib.rs`）
- `web/`: Svelte + TypeScript + Three.js。描画は `web/src/lib/Viewer.ts`、計算担当は `plot.worker.ts`（最大 4 Worker、**式ごと**に分担）、依頼窓口は `plotClient.ts`、全体の状態は `App.svelte`
- テストと確認: `core/` で `cargo test`、`web/` で `npm run check` と `npm test`、`npm run build`
- 公開先は GitHub Pages（**HTTP ヘッダーを設定できない** → COOP/COEP が要る `SharedArrayBuffer` は、そのままでは使えない）
- 決まりごと: コードのコメントと README は日本語。機能を変えたら README の該当箇所も直す
- README の「描画を軽くする工夫」に、今の最適化がまとまっている。最初に読むこと

## 課題（難しい順ではない）

各課題に「現状 → 何が難しいか → 調べてほしいこと → 計画で決めてほしいこと」を書いてあります。
ファイル名と関数名は手がかりです。行番号は変わっている可能性があります。

### 課題 1: 視点やグラフを回すと粗くなる

**現状**
- 視点を動かしている間: 三角形が 6 万個を超える曲面は、頂点クラスタリングで作った粗い版（約 3 万個、`mesh.rs` の `add_cluster_lod`）に切り替わる。さらに、1 コマが遅いと画素密度を最小 0.3 倍まで下げる（`Viewer.ts` の `MOTION_SCALES`、`setPixelRatio`）
- 回転・スライダー・断面を再生している間: 細かさを半分にして計算し直す。陰関数は $\left(\tfrac12\right)^3 = \tfrac18$ の計算量になる（`App.svelte` の `isCoarse`、`Math.round(resolution / 2)`）
- n 次元の回転: `Shape.project`（`lib.rs`）が Worker の中で射影し直してメッシュを送り返す。回転した陽関数で、回転が「表示中の座標どうし」でなくなると `RECOMPUTE` になり、陰関数として計算し直す

**何が難しいか**
- 頂点クラスタリングは速いが、形が崩れやすい（細い部分が潰れ、輪郭がガタガタになる）
- 画素密度を下げると全体がぼやける。下げずに 60fps を保つ方法が要る
- 媒介変数の図形の n 次元回転は、射影 $\mathbf{q} = P\,R(\theta)\,(\mathbf{p} - \mathbf{c})$（遠近がある場合はその後に割り算）だけで決まり、**つながり方（三角形）は変わらない**はず。それなのに毎回 Worker で計算し、データを送り返しているなら無駄が大きい
- 回転した陽関数・陰関数は、回すたびに形そのものが変わるので、計算し直しを避けられない

**調べてほしいこと**
- 粗い版に切り替わる条件と、そのとき実際に何がどれだけ遅いのか（GPU の三角形数か、画素数か、JS 側か）
- n 次元の射影を、頂点シェーダーで行えるか（d 次元の点を属性として GPU に置き、$R(\theta)$ を uniform で渡す）。d が大きいときの属性の数の上限と、その回避策
- 粗い版の作り方を、二次誤差（QEM）による簡略化や、メッシュを作るときの格子を間引く方法に変えた場合の、品質と生成時間の比較

**計画で決めてほしいこと**
- 「動かしている間の見た目の質」をどう測るか（例: 止まった状態との画素の差、三角形数、fps）
- 再計算が要らないもの（GPU で回せるもの）と、要るもの（計算を段階的に細かくする必要があるもの）の線引き
- 段階的に細かくする方式（粗い版をすぐ出し、裏で細かく計算して差し替える）を入れるか。入れるなら、ちらつきをどう抑えるか

### 課題 2: 発散する点の近くで曲面が綺麗にならない

**現状**
- 陽関数は一様な格子（既定の細かさ 150、`explicit_surface_full`）で計算する。表示範囲を超える値は、範囲の 1 つ分外 $[\,\ell - h,\; u + h\,]$ にそろえて描き、はみ出た部分は Three.js のクリッピングで切り落とす（頂点を捨てると穴が空くため）
- 段差（$\tan$ の極、$\mathrm{floor}$ など）は `find_jumps` が、格子の辺を二分法で 12 回狭めて見つけ、三角形を切り分ける
- 陰関数は一様な格子の Surface Nets 法（値は f32 で保存）

**何が難しいか**
- 極の近く（例: $z = \dfrac{1}{x^2 + y^2}$、$|\Gamma(x + iy)|$）では、曲面が急に立ち上がる部分に格子点がほとんど無い。そのため、壁がギザギザになり、クリップ面での切り口も階段状になる
- 一様な格子を細かくすると、計算量が $O(n^2)$（陰関数は $O(n^3)$）で増える。急な所だけを細かくする**適応的な分割**が必要
- 適応的に分割すると、細かさの違う所の境目に T 字の継ぎ目ができ、ひびが入る（細かさの差を 1 段までに抑える四分木や、継ぎ目を埋める三角形が要る）
- 陰関数で、$F$ が $+\infty$ から $-\infty$ へ飛ぶ所（例: $\tan$ を含む式）を、曲面として誤って描いていないか。描いているなら、本当の零点と区別する必要がある

**調べてほしいこと**
- 今のやり方で、典型的な式（`1/(x^2+y^2)`、`abs(gamma(x+iy))`、`tan(x) y`、`1/x + 1/y`、陰関数 `z (x^2+y^2) = 1`）がどう崩れるか。スクリーンショットか、具体的な格子の値で確認する
- 分割の基準の候補: 高さの差、曲率（2 階差分）、**画面上での誤差**（カメラによって変わるので、作り直しの頻度とのかね合い）、表示範囲の上下の面との交差
- 表示範囲との交線を、クリッピングに任せず、二分法で正確に求めて曲面を範囲内で切る方式にした場合の効果

**計画で決めてほしいこと**
- 陽関数と陰関数を同じ仕組みで扱うか、別々にするか
- 適応的な分割の深さの上限と、三角形数の上限（課題 4 の性能目標と矛盾しないこと）
- 今の粗い版（LOD）、格子線の表示（`grid_coords`）、複素数の色分けの値（`complex_values`）が、適応的な格子でも壊れないこと

### 課題 3: 小さい図形の形が粗い（または消える）

**現状**
- 陰関数・陽関数・範囲で重ねた立体は、**表示範囲全体に一様な格子**を張る。表示範囲に比べて小さい図形（例: 範囲 $[-10, 10]^3$ の中の半径 $0.1$ の球、細い輪、細い管）は格子数個分しかなく、角ばるか、格子の間に収まって**丸ごと消える**
- 媒介変数の曲線は適応的に分割している（`curve_nd`、最大 14 回、最大 20 万点）。曲面と立体（`parametric_surface_nd` など）は一様
- 範囲で重ねた立体（`implicit_solid`）は、$\min_r F$ と $\max_r F$ を `samples` 等分の点から近似している（細い所を見落とす）

**何が難しいか**
- 一様な格子の点だけを見ても、格子より小さい図形は「どこにあるか」がわからない。見つけるには、区間演算（$F(B) \subset [a, b]$ で $0 \notin [a,b]$ なら箱 $B$ には曲面が無いと言える）か、勾配を使った見積もりが要る
- 計算はすべて複素数で、ガンマ・ベッセル・超幾何などの特殊関数がある。こうした関数の正しい区間の上下を出すのは非常に難しい
- 八分木で細かくすると、Surface Nets の継ぎ目の処理と、近い曲面どうしを分ける今の処理（README の「1 つのセルを 2 枚以上の曲面が通るとき」）を作り直すことになる

**調べてほしいこと**
- `eval.rs` にはすでに「定数がすべて実数で、関数が初等関数だけなら実数だけで計算する」道がある。この範囲に限って区間演算を入れられるか（初等関数だけ・実数だけ、それ以外は今のまま）
- 区間演算が使えない式でどうするか（例: 勾配から作る、リプシッツ定数のような見積もり。見落としがあり得ることを認める）
- 媒介変数の曲面の適応的な分割（曲線の `curve_nd` と同じ考え方を 2 次元に広げる）

**計画で決めてほしいこと**
- 区間演算を、課題 2（発散）と課題 4（曲面の無い所を飛ばして速くする）と共通の土台にするか
- 「小さいものを見落とさない」ことと「速さ」のどちらを優先するか、その切り替え（⚙ の設定にするか）

### 課題 4: もっと速く（目標は 60fps、重い式でも 30fps）

**現状**
- 1 つの式は 1 つの Worker で計算する（複数の式なら並列）。WASM の SIMD もスレッドも使っていない
- 計算結果のメッシュは、Worker から JS に配列で送る（コピーか、所有権の移動かを確認すること）
- 陰関数（細かさ 200）で約 0.60 秒（README）

**目標の言い換え**: 1 コマの持ち時間は 60fps で $\dfrac{1000}{60} \approx 16.7\,\text{ms}$、30fps で $33.3\,\text{ms}$。
「視点を動かすだけ」は描画だけ、「スライダー・回転の再生」は計算 + 転送 + 描画を、この時間に収める必要がある。

**何が難しいか**
- 1 つの式を複数のスレッドで分けるには、`SharedArrayBuffer`（COOP/COEP ヘッダー）が要る。GitHub Pages ではヘッダーを設定できないので、Service Worker でヘッダーを付ける回避策（coi-serviceworker のような方法）の是非を判断する必要がある。または、範囲を分けて複数の Worker に配る（メモリを共有しない）方式もある
- WebGPU の計算シェーダーで式を計算する案は、命令列を WGSL に変換する必要がある。さらに f32 の精度で特殊関数を計算できるかという問題がある
- 何が遅いのかを測らずに手を入れると、効果の無い最適化になりやすい

**調べてほしいこと（最初に必ず測る）**
- 代表的な式ごとに、時間の内訳を測る（式の計算・メッシュ生成・転送・Three.js への登録・描画）。測る仕組みが無ければ、それを最初のステップにする
- WASM SIMD（`+simd128`）を有効にしたときの `eval_batch` の速さ
- 範囲を分けて複数の Worker に配る方式（陽関数は帯に分け、陰関数は z の層に分ける。継ぎ目の頂点の扱いを考える）
- 再生中に、前の結果を使い回せる所（パラメータが関わらない部分式の値、格子の座標など）

**計画で決めてほしいこと**
- 測った数字に基づく、効果の大きい順の手順
- 計算が持ち時間に収まらない式を、どう見せるか（前のコマを出し続ける、粗い版を出す、など）

### 課題 5（README の「今後の予定」の残り）

計画の対象にするかどうかも含めて判断してください。

- 多変数の図形（媒介変数 $k \ge 4$ 個）を射影した**輪郭だけ**を描く。輪郭は、射影したヤコビ行列の階数が落ちる所 $\operatorname{rank}\!\left(P\,\dfrac{\partial \mathbf{p}}{\partial (t_1, \dots, t_k)}\right) < 3$ にできる。$k$ 次元の媒介変数空間の中でこの集合を探すのは重く、数値的にも不安定
- 表示範囲の端の面にも、立体のふたをする（今は切り口の平面だけ）。媒介変数の立体では、内側の判定が難しい
- 辺だけの表示（これは比較的易しい）
