# 計画: そのほかの見せ方（等角写像・流れの絵・極小曲面・周転円）

文書 4（`docs/plan-roadmap.md`）。等角写像の格子の変形、常微分方程式の吸引域とポアンカレ断面、ベクトル場の LIC・FTLE（`plan-render-algorithms.md` 0.2 の Q8）、
極小曲面（ワイエルシュトラス・エンネパーの表現と、平均曲率 $H = 0$ の確かめ）、フーリエ級数と周転円を、1 ステップずつ（1 ステップ = 1 PR）の指示書にする。
ステップの名前は、流れの絵（吸引域・ポアンカレ断面・LIC・FTLE）が **B0〜B7**、等角写像が **C0〜C3**、極小曲面が **J0〜J2**、フーリエ級数と周転円が **E0〜E3**。
各ステップの「担当」は `docs/agent-tiers.md` の段階。各ステップの「実装の土台」は、関数の形・データの形・処理の流れの下書き。
**土台は出発点で、命令ではない**。コードを読んで合わない所があれば直してよく、そのときは 0 章の表に「計画との違い」を書く。

**この文書の芯**: 5 つの話題はばらばらに見えるが、新しく作る土台は 2 つだけ。

- **画素ごとの値の画像**（B0）: 吸引域・FTLE・LIC は、どれも「平面の点ごとに流れを追って、1 つの数を出す」。計算エンジンが数の画像を返し、画面が色を付ける
- **点をまとめて流す解法**（B1）: 今の常微分方程式の解法（`ode.rs`）を、何万個の点を一度に進める形にする。1 点ずつでは 256² 画素に 18 秒かかる（1.2）

残りは今ある仕組みに乗る。等角写像は座標系（`plan-hard-tasks.md` 9 章の S36〜S39。**試すと、複素数の写像でもう動く**）、極小曲面は媒介変数の曲面と曲率の色分け（N2）、
周転円は複素平面の曲線と点・線、ポアンカレ断面は今の解法に「横切った所を拾う」仕組みを足すだけ。

## 2. 全体の決めごと

### 2.1 話題ごとに乗せる道

| 話題 | 乗せる道 | 出力 | 2D・3D |
|---|---|---|---|

| ポアンカレ断面（B6） | 今の解法 + 1 歩ごとの呼び出し | 点（`Plot::Points`） | どちらも（3D は平面の上の点、2D は断面の座標の図） |

### 2.2 画像はエンジンが数を返し、色は画面が付ける

文書 3 の 2.2 と同じ決まり。エンジンは画素ごとの数（1〜2 チャンネルの f32）を返し、色・濃さ・範囲は画面のシェーダーが決める。色の設定を変えても計算し直さない。

| 種類 | チャンネル 1 | チャンネル 2 | 色の付け方（画面） |
|---|---|---|---|
| 分類（吸引域） | 行き先の番号（0, 1, 2, …。$-1$ は無限へ、$-2$ は打ち切り） | 落ち着くまでの時間を 0〜1 にしたもの（無ければ 0） | 番号ごとの色（8 色の表）、時間で明るさ。$-1$ は黒、$-2$ は灰 |
| 値（FTLE） | 前向きの FTLE | 後ろ向きの FTLE（求めなければ NaN） | 前向きは白 → 赤、後ろ向きは白 → 青を重ねる。範囲は値の 99 % が入る所 |
| 筋（LIC） | 濃さ（0〜1） | $\lVert\mathbf F\rVert$ | 濃さ × ベクトル場の色の対応表（`vivid`）。⚙ で白黒だけにもできる |

### 2.3 点をまとめて流す解法の決まり

- **今の `ode::solve` と同じ解き方**（同じ係数・同じ誤差の許し方）を、点ごとに刻み幅を持ったまま、全部の点で 1 歩ずつ進める。右辺は、まだ進めている点だけを詰めた配列で `eval_batch` を呼ぶ
- そうすると、**1 点ずつ `ode::solve` で解いた答えと（丸めを除いて）同じになる**。テストはこの一致で書く（固定刻みの RK4 は、1.2 では一致したが、硬い所で黙って違う答えになるので使わない）
- 止める条件（吸引域の「落ち着いた」、表示範囲の 8 倍の箱を出た、など）は呼び出し側が渡す。止まった点は配列から外す（文書 3 の F0 と同じ詰め方）
- 1 点の歩数の上限は 2 万歩。上限で止まった点は「打ち切り」として返し、画面は灰色、説明に数を出す
- 動かしている間（`PLOT_NO_REFINE`）は画素を 1/4 の細かさで、止まったら 1/2（上限 512²）で計算する（2.4 の画面までの道）

**画面までの道**（画像の層。B0 で作り、B3〜B5 が使う）

1. `core/src/lib.rs`: `plot` の中、`build` の直後で `FLOW_STYLE` を見て、ベクトル場・常微分方程式の行なら画像を作る（`flow_style` の `kind`: 0 なし、1 LIC、2 FTLE、3 吸引域）。

### B1: 点をまとめて流す解法

- **担当**: A（理由: 点ごとに刻み幅を持ったまま詰めて進めるので、歩の受け入れ・やり直し・外す点の番号の付け替えを間違えやすく、間違えても「少し違う絵」になるだけで気づきにくい）
- **平たい説明**: 吸引域や FTLE では、画面の画素の数（6 万個ほど）だけ常微分方程式を解く。1 つずつ解くと、式を読む手間が毎回かかって遅い（1.2 で 1 画素 0.27 ms）。
  全部の点を並べて、「全部の点を 1 歩ずつ」進めると、式を読む手間が 1 回で済む
- **触るファイル**: `core/src/flowmap.rs`（新規）、`core/src/ode.rs`（係数を `pub(crate)` にして共有）、`core/tests/flow_pictures.rs`（新規）
- **やること**
  1. `flow_batch`: 点ごとに状態・時刻・刻み幅を持ち、`ode.rs` と同じドルマン・プリンス法の 1 歩を、まだ進めている点の全部に試す。誤差の見積もりで、点ごとに受け入れ・やり直しを決め、刻み幅を直す（`ode::solve` と同じ式）
  2. 右辺は、進めている点だけを詰めた列で `eval_batch` を呼ぶ（変数は状態と $t$）
  3. 止める: 時刻 $t_1$ に着いた（最後の歩は $t_1$ ちょうどに合わせる）、呼び出し側の `stop` が真、表示範囲の 8 倍の箱を出た（今の `ode_built` と同じ）、
     有限でない値、2 万歩。止まった点は配列から外す（詰め直す）
  4. 結果は点ごとの最後の状態・止まった理由・止まった時刻・歩数
- **実装の土台**

  ```rust

  pub enum Stop { Reached, Asked, Escaped, NotFinite, StepLimit }
  pub struct FlowEnd { pub state: Vec<f64>, pub t: f64, pub stop: Stop, pub steps: u32 }
  pub struct FlowOptions { pub t0: f64, pub t1: f64, pub limit: f64, pub max_steps: u32 }
  /// starts: 点ごとの初めの状態。stop(点の番号, 状態, 時刻) が真なら、その点を止める
  pub fn flow_batch(sys: &FlowSystem, starts: &[Vec<f64>], opt: FlowOptions,
                    stop: &mut dyn FnMut(usize, &[f64], f64) -> bool) -> Vec<FlowEnd> {
      // live: まだ進める点の番号。y[c][k]: 成分 c の k 番目（live の順に詰めた列）。h[k]・t[k]
      // loop {
      //     7 段の k を、段ごとに eval_batch（入力は y + a·k の詰めた列と t + c·h）
      //     誤差 → 受け入れた点は y・t を進めて stop を見る。止まった点は live から外して詰め直す
      //     刻み幅 h[k] を ode.rs と同じ式で直す

  }
  ```

- **完了の条件**（`core/tests/flow_pictures.rs`）
  - 減衰のある振り子 $x' = y,\ y' = -\sin x - 0.5y$ の 64² 点（$x \in [-10, 10]$・$y \in [-6, 6]$）を $t \in [0, 30]$: 全部の点の最後の状態が、1 点ずつ `ode::solve` で解いた最後の点と相対 $10^{-9}$ 以内
  - 右辺に $t$ を使う式（$x' = y,\ y' = -0.1y + x - x^3 + 0.3\cos t$）で、同じ一致
  - $x' = x^2$（$x_0 = 1$ で $t = 1$ に発散）: 止まった理由が `Escaped` か `NotFinite`。ほかの点の答えが変わらない（NaN が混ざらない）
  - 時間: ダフィング $x'' = -0.25x' + x - x^3$（連立の形）の 256² 点を $t = 40$ まで、止める条件なしで 1.5 秒以内（1 点ずつなら 18 秒。1.2）
- **壊してはいけないもの**: `ode::solve` の答え（共有した係数で、1 文字も変わらない。今の `stage5.rs` などのテストがそのまま通る）

### B2: LIC・FTLE の試作の絵と、採否の判断（Q8）

- **担当**: B（理由: アルゴリズムは定番だが、判断に使う絵の質と比べ方を整える必要がある）
- **平たい説明**: LIC は、白黒の砂嵐の模様を、流れに沿ってなぞって平均した絵。流れの向きが「筋」になって見える。FTLE は、近くにいた 2 点が時間 $T$ の後どれだけ離れるかの率で、
  流れが「分かれる線」が明るい線として見える。どちらも矢印より流れの全体が見えるはず、というのが Q8。入れる前に絵を作って、利用者に決めてもらう
- **触るファイル**: `core/src/lic.rs`（新規。B3 でもそのまま使う）、`core/tests/lic_preview.rs`（新規。`#[ignore]`）、`docs/visual/lic/`（絵の置き場）
- **やること**
  1. `lic(field, noise, w, h, length)`: 画素ごとに、場に沿って前と後ろへ `length` 歩（1 歩 0.7 画素。場の向きだけを使う）たどり、通った画素の雑音を平均する（1.2 の試作と同じ）。
     場は、画素の角の $(w + 1) \times (h + 1)$ 点で一度だけ計算し、間は双一次の補間（式を何度も計算しない）
  2. 雑音は、平面の格子（画素の大きさの正方形。原点にそろえる）の番号から作る（`hash(i, j)`）。表示範囲を画素の整数倍だけ動かすと、同じ模様がそのままずれる
  3. 試作の絵: 次の 4 つの場を 512² の BMP（圧縮しない。依存を増やさず、ブラウザで開ける）に書く。同じ場の矢印の画面の絵（`tools/visual` の撮り方）と並べる

### B4: FTLE

  $\text{FTLE} = \dfrac{1}{\lvert T\rvert}\ln\sigma_{\max}$。前向き（$T > 0$）で大きい線は、流れが左右に分かれる境目。後ろ向き（$T < 0$）で大きい線は、流れが集まってくる所

### E1: 周転円 `epicycles`

- **担当**: B（理由: E0 の FFT の上に、線の作り方を足す。答えの確かめ方ははっきりしている）
- **平たい説明**: 閉じた曲線 $\gamma(t)$ を、回る円をつないだもので描く。$\gamma(t) = \sum_k c_k e^{ikt}$ の 1 項 1 項が、半径 $\lvert c_k\rvert$ で $k$ 回の速さで回る円。
  円の端に次の円の中心を付けていくと、最後の端が曲線をなぞる

  $$c_k = \frac{1}{M}\sum_{j=0}^{M-1}\gamma(t_j)\,e^{-ikt_j},\qquad t_j = \frac{2\pi j}{M}$$
- **触るファイル**: `latex.ts`、`parser.rs`、`equation.rs`、`core/src/fourier.rs`、`core/src/lib.rs`（`MeshResult` に `epicycles` と getter）、`web/src/lib/types.ts`・`plot.worker.ts`・`Viewer.ts`、`core/tests/fourier.rs`
- **やること**
  1. `@epicycles(γ, N, τ)`: $\gamma$ は (a) $t$ の複素数の式（`e^{it}+0.3e^{-3it}`）、(b) 組 `(x(t), y(t))`、(c) 点のリスト `[(x_1,y_1),…]`（閉じた折れ線を、長さで等分した $t$ でたどる）のどれか。
     $N$ は円の数（1〜500）、$\tau$ は今の時刻（$[0, 2\pi]$。スライダーにして ▶ で動かす）
  2. 係数は $M = 1024$ 点の FFT。並べ方は $c_0$ を最初に、残りを $\lvert c_k\rvert$ の大きい順（D14。⚙ で $k$ の順）
  3. 描くもの: (i) $N$ 項の曲線の $t \in [0, \tau]$ の部分（主な曲線。式の色）、(ii) 全体 $t \in [0, 2\pi]$ を薄く、(iii) 円（中心は $k$ 番目までの和、半径 $\lvert c_k\rvert$、1 つ 64 点）と腕（中心どうしの線分）、
     (iv) ペン先の点。(ii)(iii) は測地線と同じ「面とは別の線」の配列 `epicycles`（`Viewer.ts` は式の色を薄くした細い線で描く）、(iv) は点
  4. 説明に「周転円 50 個（係数は 1,024 点の FFT。元の曲線とのずれの最大 0.012）」
- **実装の土台**

  ```rust

  pub fn epicycles(samples: &[C], n: usize, by_size: bool) -> Epicycles;

  pub fn arms(e: &Epicycles, tau: f64) -> (Vec<f32> /* 円と腕の線。NaN で区切る */, [f64; 2] /* ペン先 */);

  ```

- **やらないこと**: 3D の周転円、円の色分け、手で描く入力（E2）

  - 正方形 `[(1,1),(-1,1),(-1,-1),(1,-1)]`: 曲線と正方形の距離の最大が、$N = 50, 100, 200$ の順に減り、各段で 0.7 倍以下
  - 組 `(cos(t), sin(2t))`（8 の字）と、複素数の式 `cos(t)+i sin(2t)` の係数が同じ

- **壊してはいけないもの**: 複素平面の曲線・点のリスト・測地線の線の描き方

## 6. 危ない所

- **B1 のもっともらしい間違い**: 点ごとの刻み幅・詰め直しの番号を取り違えると、「だいたい合っているが少し違う」吸引域・FTLE になる。必ず 1 点ずつの `ode::solve` との一致（B1 の完了の条件）を、
  変更のたびに回す
- **B1 の遅い点**: 硬い方程式（ファン・デル・ポールの $\mu$ が大きい）は、一部の点だけ刻みが細かくなり、全体の時間をその点が決める。2 万歩で止めて「打ち切り」にし、灰色と説明で知らせる
- **B5 のまとめ方**: 2 つの行き先が $\varepsilon_2$ より近いと 1 つになり、輪と近くの平衡点もつながりうる。まとまりの数と代表の点を説明に出し、合わなければ行き先のリスト（D5）を書くよう README に書く
- **吸引域の境目がフラクタル**（強制振動の振り子など）: 画素の細かさで模様が変わる。間違いではないと README に書く
- **計算担当が止まる**: 吸引域・FTLE は 1 回の計算が 1 秒を超えうる。Worker の中の WASM の呼び出しは途中で止められないので、粗い画像（1/4）を先に返し、細かい画像は別の呼び出しにする。
  スライダーを動かしている間は粗い画像だけ（2.3）
- **LIC の模様が泳ぐ**: 雑音を画面の画素に結び付けると、表示範囲を動かすたびに模様が流れて見える。平面の格子に結び付ける（B2 の 2）。拡大縮小では模様の細かさが変わるのは許す
- **FTLE の差分の幅**: 画素の間隔で差分を取るので、拡大すると値が変わる（尾根は細くなる）。「近似」と出す。$T$ が大きいと $\lambda_{\max}$ があふれるので、$\ln$ を取る前に、$D\Phi$ を最大の成分で割っておく
- **C0 の枝の切れ目と極**: $\sqrt z$・$\log z$ の像は、切れ目で長い線が引かれやすい。切る基準（となりとの距離が表示範囲の 0.5 倍）が粗いと残り、細かいと正しい線まで切る。テストに $\sqrt z$ を必ず入れる
- **移行の途中の絵**: $(1-s)z + sf(z)$ にも臨界点があり（$1/z$ なら $z = \pm\sqrt{s/(1-s)}$）、途中で網が折れ返ることがある。間違いではないと README に書く
- **J0 の積分の道**: 範囲の中に $f$ の極があると、そこを通る列の先が全部おかしくなる。有限でない値が出たら、その列の残りを捨てる（J0 の 4）。カテノイドなどは極の格子で原点を避ける
- **J1 の基準**: 表示範囲がとても大きい・小さいと、$10^{-6}/L$ の基準が本物の小さな曲率を「≈ 0」にしうる。説明に $\lvert H\rvert$ の上限の数を必ず出す
- **E0 の跳びのある関数の標本**: 跳びの所の値を標本にすると、係数に $O(1/M)$ の誤差が入る。升の中点で標本を取る（E0 の 2）。それでも跳びが升の中にあれば誤差は残るので、テストの許し方は $10^{-6}$ に止める
- **E2 の触る操作**: なぞる操作がパン・ピンチと取り合いになる。描く状態の間は、ほかの操作を全部止める
